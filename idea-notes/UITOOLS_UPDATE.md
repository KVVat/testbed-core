### 端末側のオーバーヘッドの正体

JSONのデータサイズ自体は画像に比べて非常に小さい（数KB〜数十KB）ため、ネットワーク帯域は全く問題になりません。
問題は、Android端末側でAgent（`ProtocDumper` や `JsonDumper`）が **「画面上の全UIノード（`AccessibilityNodeInfo`）を再帰的に取得する処理」が、CPUとBinder（プロセス間通信）を激しく消費する** という点です。

これを動画と同じペース（例：毎秒10回）で実行すると、端末のUIスレッドが詰まり、画面がカクカクになり、最悪アプリがクラッシュします。

### 効率化のための3つのアプローチ

このOHを回避しつつ、LLMと人間に常に最新のツリーを提供するための工夫（アーキテクチャ）として、以下の組み合わせがベストプラクティスです。

#### 1. 人間用（高FPS）とLLM用（オンデマンド）の非同期化

これが最も基本となる棲み分けです。

* **画像のストリーミング**: 画面の録画（Minicapや標準のスクリーンキャストAPI）を使って、**10〜30fpsで人間向けに常に流し続けます。**
* **ツリーの取得**: 毎フレーム取るのはやめ、**「LLMが `get_ui_dump()` をコールした瞬間」** または **「人間がMonitor上で画面をクリックした瞬間」** にだけ、同期的にAgentへツリーを要求します。
* LLMは「動画」を見ているわけではなく、「ある瞬間の静止画とツリー」を見て判断するため、LLM用にはオンデマンドで取得できれば十分です。

#### 2. Agent側での「ハッシュ/キャッシュ」の導入（ご提案の通り！）

ご提案いただいた「差分をhashでとる」というアイデアは、Agent側の負荷軽減に非常に有効です。

AndroidのUIAutomatorには `AccessibilityEvent` を監視する機能があります。

* Agent内で「最後にUIツリーを出力した時点の状態（またはハッシュ）」を記憶しておく。
* 画面に変化（`AccessibilityEvent.TYPE_WINDOW_CONTENT_CHANGED`）がない間は、ツリーのトラバース処理自体をスキップし、`{"status": "not_changed"}` とだけ返す。
* これにより、UIが静止している間はポーリングによるOHが実質ゼロになります。

#### 3. 「画面静止待ち（Idle）」による自動取得

動画ストリームを流しつつ、Monitor側（Host側）で「画像に変化がなくなった（＝アニメーションやスクロールが停止した）」と判定したタイミングで、自動的に1回だけツリーをフェッチします。
こうすれば、Monitorの画面右側に表示されているツリービューが、**「画面が動いている間は更新されないが、ピタッと止まると最新のツリーがサッと表示される」** という非常にスマートなUXになります。

### まとめ：理想の Device Monitor の姿

これらを踏まえると、Device Monitor の仕様は以下のようになるのが理想的です。

1. **画面左側（映像エリア）**:
* 常に10〜30fpsで最新のデバイス映像がストリーミングされている。


2. **画面右側（ツリーエリア）**:
* 映像とは非同期で、1秒に1回（あるいは画面が静止した時だけ）最新のJSONツリーを取得して表示を更新する。


3. **LLMへの連携**:
* LLMがテストを自動生成する際は、MonitorのUIに表示されている「最新の画像＋最新のJSON」のペアをMCP経由で渡す。



「UI Inspector」は過去の特定の瞬間を重箱の隅をつつくように解析するツール（デバッガ）として残し、「Device Monitor」は **人間とLLMがペアプログラミングをするためのリアルタイムダッシュボード（画像＋軽量なツリー）** として進化させる。

この設計であれば、端末を重くすることなく、LLMテスト開発に必要な情報を完璧に揃えることができます！

### 実装に向けた「2つの重要なコツ」

もしAgent側（UIAutomator側）でこのイベントをリッスンして監視ループに組み込む場合、以下の点を知っておくと実装が非常にスムーズになります。

#### 1. フックする方法

UIAutomatorの背後にある `UiAutomation` クラスには、イベントを監視するためのリスナー登録メソッドが用意されています。

```java
// Agent（デバイス側）での実装イメージ
getUiAutomation().setOnAccessibilityEventListener(new UiAutomation.OnAccessibilityEventListener() {
    @Override
    public void onAccessibilityEvent(AccessibilityEvent event) {
        if (event.getEventType() == AccessibilityEvent.TYPE_WINDOW_CONTENT_CHANGED ||
            event.getEventType() == AccessibilityEvent.TYPE_WINDOW_STATE_CHANGED) {
            
            // 「画面に変化があった」というフラグを立てる
            isUiChanged = true;
        }
    }
});

```

#### 2. 【超重要】「デバウンス（Debounce）」処理を必ず入れる

これが一番の罠なのですが、画面内で「プログレスバーがくるくる回っている」「リストがスワイプされて慣性スクロールしている」といったアニメーション中は、このイベントが**秒間数十回という猛烈な勢いで連続発火**します。

イベントが来るたびに律儀にJSONツリーを再生成していると結局端末がフリーズしてしまうため、以下のような**「デバウンス（間引き）処理」**を必ず入れるのが鉄則です。

* **ダメな例**: イベントを受信 ➔ すぐにJSONツリーを生成 ➔ ホストへ送る
* **良い例**: イベントを受信 ➔ タイマーをリセットし、**「200ミリ秒間、次の新しいイベントが来なかったら」** 画面が静止したと見なしてJSONツリーを1回だけ生成する。

### 統合型「タイムライン・インスペクタ」のメリット

1. **「なぜ失敗したか」の究明が劇的に楽になる**:
   テストがエラーで止まった時、人間が見たいのは「エラー発生後の画面」ではなく**「エラーが起きる直前の画面とDOM構造」**です。履歴が蓄積されていれば、数ステップ前に戻って「あ、ここでローディングダイアログがまだ被ってたんだ」とDOMレベルで解析（インスペクト）できます。
2. **シームレスなUI体験**:
   「動画を見る画面」と「DOMを見る画面」を行ったり来たりするユーザーの認知負荷がなくなり、1つの画面で完結します。

### 実現のためのシステム構造（設計イメージ）

この統合ツールを快適に（メモリをパンクさせずに）動かすには、先ほど議論した「画面変化（`TYPE_WINDOW_CONTENT_CHANGED`）」と「デバウンス」の仕組みが完璧に噛み合います。

1. **スナップショットの取得タイミング（ここが鍵！）**:
   毎フレーム保存するのではなく、以下のタイミングで「画面画像＋JSONツリー」のセットをメモリ（または一時ファイル）に `List<Snapshot>` として蓄積します。
* 画面のスクロールやアニメーションが**静止した瞬間**（デバウンス後）
* LLM（または人間）が**クリックやテキスト入力を実行した直前/直後**


2. **「ライブモード」の挙動**:
   ツール下部の「再生」がオンの時は、最新のストリーミング映像を映し出します（DOMツリーは表示を更新しない、または最小限にする）。
3. **「ヒストリー（インスペクタ）モード」の挙動**:
   ユーザーがストリーミングを一時停止したり、画面下部の「履歴スライダー（またはリスト）」で過去の特定の瞬間に戻ったりすると、**UI Inspectorとして完全覚醒**します。その時点のJSONツリーが右側に展開され、クリックで要素の `bounds` や `resourceId` を深掘りできるようになります。

この構造なら、LLMへのコンテキスト渡し（「直近3ステップ分の画面遷移を教えて」など）も、蓄積したSnapshotの履歴から渡すだけで済むため、AIエージェントの推論精度向上にも直結します。
